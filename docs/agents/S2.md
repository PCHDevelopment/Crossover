## How a task goes

1. **Start only an issue assigned to you** (`agent:s2` plus an "Assigned to S2" comment) whose dependencies have merged. Comment `S2 starting`.
2. **Plan-first tasks:** post the plan on the issue: modules, names, line counts, how many PRs and in what order. **Don't write code until O1 answers.** Follow the answer's conditions exactly.
3. **Branch** from current `main`: `s2/T<id>-<slug>`. Part N of a split gets `s2/T<id>-<N>-<slug>`.
4. **Keep the PR small:** about 400 changed lines, not counting tests and lockfiles. If a part grows past that, split it into serial PRs, each from `main` after the previous one merges, and say so on the issue. **No stacks** unless O1 agreed to one beforehand.
5. **At most five open PRs** (Peter, 2026-10-19). Review blockers on an open PR come before starting anything new.
6. **Open the PR** with the repo template (`.github/pull_request_template.md`): title `[T<id>] …`, `Closes #<issue>` (only on the **last** part of a multi-part task), one line per acceptance criterion with the test that proves it, the sabotage/mutation evidence, and the validation checklist.

## Proof the spec will ask for

- **Behaviour-preserving moves:**
  - `git diff --color-moved=dimmed-zebra origin/main...` shows only moved lines plus imports and wiring. Say so in the PR body.
  - `node scripts/refactor/prove-move.mjs OLD.ts NEW1.ts …` shows no changed declarations.
  - `node scripts/refactor/prove-exports.mjs` on the package `index.ts` before and after prints an empty diff.
  - List every moved declaration and where it went.
- **Fixes:** a regression test that fails without the fix. Show it: revert the fix in a throwaway commit, run the test, and paste the failure. Then restore.
- **Fix the product, not the test.** A flaky UI test caused by a real race gets a product fix and a held-response regression test, not a `page.reload()` or a longer timeout (#315, Review 18).
- **New timeouts** follow the T1529 rule: measure idle and under 3× load, budget = load max × 7 rounded up to the next 5,000 ms, with a `// Measured (T1529): idle <x> ms, 3x load <y> ms; budget 7x.` comment.

## Getting merged

O1 merges, never you. A PR merges only when **all** of these hold:

1. CodeRabbit's latest review is **Approved** on your **current head SHA**.
2. Every CI check on that head is green.
3. No unresolved review threads.
4. No conflict with `main`.

What you do:

- **CodeRabbit findings:** fix the valid ones and reply on each thread saying what you changed (or why not, with evidence). Push. CodeRabbit re-reviews the new head. **Never** comment `@coderabbitai approve` on your own PR, and never dismiss its review.
- **Disagreeing with CodeRabbit** (Peter, 2026-10-19): if you think a finding is wrong, out of scope or not worth its cost, do both: (1) reply on its thread with your evidence and ask CodeRabbit to re-review (`@coderabbitai full review`, or a reply on the thread asking it to reconsider); (2) tag O1 on the PR in one comment, `@O1 dispute: <thread link>`, plus one line with what you propose. O1 decides: fix it, fix it another way, or not applicable (recorded on the thread). The merge gate is unchanged; if CodeRabbit still won't approve after an O1 "not applicable" ruling, O1 takes it to Peter. Keep working on other queue items meanwhile.
- **Stale CodeRabbit threads:** CodeRabbit sometimes leaves its old threads open after you've pushed the fix. When every open CodeRabbit thread is handled (fixed on your current head, or ruled "not applicable" by O1 with the reasoning posted on the thread) and CodeRabbit has reviewed that head, comment `@coderabbitai resolve` on the PR yourself. It closes all of CodeRabbit's threads on the PR, so don't use it while any finding is still open. It isn't an approval and doesn't replace one: the gate still needs CodeRabbit's **Approved** review on the head. Don't close CodeRabbit threads with GitHub's Resolve button.
- **Red CI:**
  1. Save the evidence first: run ID, job ID, failing test, first error line.
  2. Decide whether your diff touches that test's code path. If it does, it's yours to explain, even if it looks flaky.
  3. Re-run the failed job **at most once**, and only after saving the log. Post the result on the PR.
  4. A known flake is listed in [O1.md](O1.md), "Red CI".
- **Behind `main`:** merge `main` in (`git merge origin/main`). Don't rebase or force-push.
- When it's ready, comment `S2: ready at <sha>` with CI and CodeRabbit status.

## Rules that have caught people before

- Every SQL query on room data is scoped by `room_id`. Text `ORDER BY` uses `COLLATE "C"`.
- No Docker, network or Git side effects inside a DB transaction. Claim an idempotency key before the side effect.
- Errors are `CrossoverError` with a §16.3 code. No secret, token or credential in errors, events or logs.
- Every new read or stream applies the participant view (`redactEventFor` or per-path redaction, §34.5).
- New command modules are registered in `apps/server/src/compose.ts`, with an e2e test.
- Run git with `GIT_CONFIG_GLOBAL=/dev/null` so host config can't leak into tests.
