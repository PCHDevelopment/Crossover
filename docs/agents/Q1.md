## How a task goes

1. **Start only an issue assigned to you** (`agent:q1` plus an "Assigned to Q1" comment) whose dependencies have merged. Comment `Q1 starting`.
2. **Plan-first tasks:** post the plan and wait for O1's OK. Follow its numbered conditions exactly.
3. **Branch** from current `main`: `q1/T<id>-<slug>`. Part A/B of a task gets `q1/T<id>-<slug>-a` and so on.
4. **Keep the PR small:** about 400 non-test, non-fixture changed lines. Split into serial PRs, each from `main`, and agree it on the issue first.
5. **At most five open PRs** (Peter, 2026-10-19). Review blockers come before new work.
6. **Open the PR** with the repo template: title `[T<id>] …`, `Closes #<issue>` (last part only), one line per acceptance criterion with its proof, sabotage evidence, run links, and the validation checklist.

## Closing finished issues

(Peter, 2026-10-20) A task's issue closes when all its work has merged.

- The **last** PR of a task carries `Closes #<issue>`, so GitHub closes the issue when O1 merges it. Earlier parts say `Part of #<issue>`.
- After your last part merges, **check the issue is closed**. If it isn't (the keyword was missing, or the work landed in a PR that didn't close it), close it yourself with a comment naming the merged PRs, and close it as _completed_. Example: `Q1: done in #<pr> and #<pr> (merged). Closing.`
- Never close an issue while any of its acceptance criteria is unmerged. A split task stays open until its last part merges.

## How Q1 work is proven

- **A failure is reproduced before it's fixed.** Give the run ID, job ID and the exact error line, then the same check passing after the fix.
- **Sabotage checks:** break the thing on purpose in a throwaway commit, link the red run, revert. The PR body lists each one and what it showed. If a sabotage check doesn't behave as the spec predicted, **stop and tell O1** before choosing another approach. That happened on #394, where a public repo needed no token.
- **Loops:** when the spec asks for N runs under load, check that the loop **actually ran the test**. A wrong `-t` filter that matches nothing counts as "no failure" (the corrected T1559 report).
- **Version-sensitive behaviour:** test on the version that matters, meaning the server image's git and Node, not just the runner's. T1572 checked the image's git 2.54, the host's 2.53 and the runner's 2.55.
- **Timeouts** follow the T1529 rule: measure idle and under 3× load, budget = load max × 7 rounded up to the next 5,000 ms, minimum 15,000 for rehearsal steps, with a `// Measured (T15xx): …` comment.
- **The runbook is the spec** for the rehearsal. If the rehearsal needs a step the runbook lacks, that's a runbook bug: fix it in the same PR and list it.
- **A product bug the rehearsal finds** is reported on the issue with evidence and becomes its **own** `T` issue (O1 writes it). Don't work around it inside the rehearsal.

## Getting merged

O1 merges, never you. A PR merges only when **all** of these hold:

1. CodeRabbit's latest review is **Approved** on your **current head SHA**.
2. Every CI check on that head is green.
3. No unresolved review threads.
4. No conflict with `main`.

What you do:

- **CodeRabbit findings:** fix the valid ones and reply on each thread. If a finding conflicts with O1's spec, say so on the thread and ask O1. **Never** comment `@coderabbitai approve` on your own PR, never dismiss its review, and don't push no-op commits to trigger a review. If CodeRabbit doesn't re-review, tell O1.

O1 decides: fix it, fix it another way, or not applicable (recorded on the thread). The merge gate is unchanged; if CodeRabbit still won't approve after an O1 "not applicable" ruling, O1 takes it to Peter. Keep working on other queue items meanwhile.
- **Red CI:**
  1. Save the log first: run ID, job ID, failing test, first error line.

- The workflow token defaults to `contents: read`. `test` and `web-e2e` also get `actions: read`, and `check` gets nothing. Third-party actions are pinned to commit SHAs with the version in a trailing comment (T1571).
